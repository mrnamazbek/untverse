# ADR-002: Модульная слоистая архитектура бэкенда

## Статус
Принято (Accepted)

## Контекст
Во избежание монолитной запутанности и смешивания бизнес-логики с представлением и доступом к данным, бэкенд должен следовать чистой слоистой архитектуре с четко очерченными доменами (courses, topics, quizzes, coding, gamification, analytics, admin).

## Решение
Бэкенд структурируется по строгой вертикально-горизонтальной модели:
1. **API Endpoints (`app/api/v1/endpoints/`)**: Только валидация DTO схем, распаковка запроса, вызов соответствующего сервиса и формирование HTTP-ответа.
2. **Services (`app/services/`)**: Вся бизнес-логика (проверка условий, подсчет баллов, логика интервального повторения, расчет опыта).
3. **Domain Events (`app/core/events.py`)**: Слабая связанность (decoding) через диспетчер доменных событий. Сервис прохождения квизов генерирует событие `QuizCompletedEvent`, на которое независимо подписывается `GamificationService`.
4. **Repositories (`app/repositories/`)**: Абстракция доступа к базе данных через SQLAlchemy 2.0 AsyncSession.
5. **Database Models (`app/models/`)**: Декларативные модели сущностей с валидацией целостности данных.

## Последствия
- Высокая тестируемость модулей через фикстуры и моки.
- Независимое развитие и возможность в будущем вынести подсистемы (например, геймификацию или запуск кода) в микросервисы без переписывания кодовой базы.
